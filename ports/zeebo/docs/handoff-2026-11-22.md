## 1. Objetivo

Portar o **Sonic Adventure 1** (fonte C do decomp matching
`reshaped/sonic-adventure`, JP HDR-0001 v1.007) para o **Zeebo**:

- CPU ARM1136J-S (ARMv6, **sem VFP/NEON**, float em software);
- GPU Adreno 130 (Imageon 3D), **GLES 1.x fixo**, T&L de hardware, **sem
  shaders nem iluminação de hardware**;
- BREW 4.0.2, SDK Zeebo 1.2.4;
- validação **só no zeebx** (não há console real; o GEC não foi localizado).
  O **BREW Simulator 4.0.2** (x86/DLL, via Wine) **não executa `.mod` ARM**;
  serve só como segunda opinião de lógica se houver alvo x86.

Sem rehost do binário SH-4 e sem o `engine/pc` (Vulkan) do upstream.

## 3. Build, execução e testes

Tudo a partir de `ports/zeebo/` (ou `make -C`):

```sh
make                         # applet -> build/zeebo/sa1z.mod + .mif
make host-selftest           # matemática do Ninja no host
make -f game.mk mod          # jogo+applet -> build/zeebo/sa1g.mod
make -f game.mk link         # 1ST_READ ARM32 (game.o parcial)
./check.sh                   # gate: build, selftest, zeebx (sa1z), pad, timer
CHECK_GAME=1 ./check.sh      # + game.mk, integrate (0 duplicatas) e menu
./play.sh                    # abre o jogo na janela (teclas)
./play.sh --build            # recompila antes
tools/frame_hash.sh          # run curto com hash do último quadro (ver §9)
```

- Disco: `tools/stage_disc.sh <raiz extraída> build/zeebo` (hard links, nomes
  minúsculos sem `;1`). O zeebx v0.6.0 ignora symlinks.
- Rodar direto:
  `~/projects/zeebx-v060/target/release/zeebx run build/zeebo/sa1g.mod --seconds=N`
- Pré-requisitos **não versionados**: `arm-none-eabi-gcc`, SDK/BREW
  (`VENDOR=`, padrão `../zeebo_demoscene/vendor`), SH4ZAM em `tools/sh4zam`,
  `make pc` do decomp (gera `build/gen/`), e os assets do disco do usuário
  (`extract/` local, fora do git).
- Nada de asset/ROM/`1ST_READ.BIN` no git.

## 8. Investigação do 3D (leia antes de mexer)

**Fato central:** a seleção de personagem desenha o Sonic pelo **`zlive`**
(`sa_present_live` → `draw_basic` → `draw_meshset`), **não** pelo
`njModel.c`. Instrumentação (contadores em potências de 2) mostrou:

- `live.present` = `live.desenha` = 4096, `live.meshset` = 16384;
- **zero** chamadas de `njm.*` e de `lt.*` nessa cena.

Portanto o trabalho de luz em `lt_arm.c` (`5d536c7`, `492168c`) **não atua no
preview**; ele deve importar para o 3D in-game (quando `njModel` rodar). Não
repita a conclusão de que "a luz não funciona" sem separar os caminhos.

**Por que o Sonic sai chapado:**

- `model->normals` existe mas é **`(0,0,0)`**; `meshset->normals` é **NULL**.
  O `shade` ficava fixo em 0,45 (`0,45 + 0,55*clamp(d·l)` com `d=0`).
- O preview não passa por `model_calc_face_normals`.
- Correção aplicada: `face_shade()` no `zlive.c` calcula a normal do triângulo
  na hora (commit `5f4cb5b`). Hash da cena `8527bc0913e4` → `7657ff96fe78`;
  o sombreado aparece, mas a forma/pose saía errada.
- **Pose resolvida (noite):** eram dois XMTRX no .mod (njm-* do applet via
  SH4ZAM vs. banco `X` do `asm.c`). `ninja/zxmtrx.c` unifica; hash
  `4e7887e2d0f7` (quadro 1186), Sonic em pé e de frente. Ver roadmap.

**Culling (Q15):**

- `glEnable(GL_CULL_FACE)` + `GL_BACK` **remove o Sonic inteiro**; `GL_FRONT`
  dá o mesmo (o argumento é ignorado no IGLES11 do zeebx); `glFrontFace` não
  existe no SDK. Culling via GL não é usável.
- A tentativa em software (área assinada no `send_strip`) **ficou inválida**:
  a chamada do caso *quad* (multi-linha) não recebeu o parâmetro `cull`.
  Revertida. Para refazer: atualizar as **3** chamadas, usar quadro fixo
  (`FRAME=`) e contar faces descartadas.
- A hipótese do giro de 180° caiu: a causa era o XMTRX duplicado. Refazer o
  Q15 depois da correção.

**Referências de hash** (`tools/frame_hash.sh`, 62 s, seleção de personagem):
- antes do `face_shade`: `8527bc0913e4` (quadro 1189);
- depois: `7657ff96fe78`;
- quadro 1188 sem correção: `5a078ba44c6e`.
